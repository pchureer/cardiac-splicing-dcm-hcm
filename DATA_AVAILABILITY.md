# Data and code availability — submission text

Two variants of the same statement, one per journal. Both are drafted from the same
facts; only the framing and the length differ. **Reserve the Zenodo DOI before you paste
either one** — see section 3.

---

## 1. Cardiovascular Research

CVR requires a data availability statement for every article type, "even if no data are
presented or discussed", and mandates no particular wording. Section order in the
back matter is **Funding → Acknowledgements → Disclosures → Data availability**.

> **Data availability.** This study is a reanalysis of publicly archived data; no new
> sequencing data were generated. The primary RNA-sequencing datasets retrieved for this
> work are available from the Sequence Read Archive and the European Nucleotide Archive
> under the accessions listed in Table 1. Three retrieved datasets were not analysed, for
> the reasons given in the Methods. All analysis code, the event-level result tables and
> the processing conventions required to reproduce every count reported here are deposited
> at Zenodo (DOI: 10.5281/zenodo.23681815) and mirrored at
> https://github.com/pchureer/cardiac-splicing-dcm-hcm. Individual-level
> genotype output from the sample-identity screen is not redistributed; the code that
> generates it from the primary data is included in the deposit.

⚠ **"retrieved", not "analysed".** Seven accessions are listed in Table 1 and three of
them were not analysed. An earlier draft said "analysed in this study" above a list of
seven, which contradicts the Methods. The wording above is the fix: *retrieved* for the
list, with a separate clause for the three.

## 2. Scientific Reports

SR requires the statement under the heading **Data availability** and asks that it name
where each dataset sits. Code goes in the same statement or in a separate **Code
availability** section; SR accepts either, and separating them reads more clearly here.

> **Data availability.** All RNA-sequencing data analysed during this study are publicly
> available and were not generated by the authors. Accessions for every retrieved dataset
> are listed in Supplementary Table 11; three of those datasets were retrieved but not analysed, for the
> reasons given in Methods. The event-level result tables generated during this study —
> the full rMATS output for every contrast, at both read lengths — are deposited at Zenodo
> under DOI 10.5281/zenodo.23681815. These tables total approximately 4.4 GB uncompressed (1.7 GB compressed) and exceed the
> supplementary-material size limit, which is why they are deposited rather than attached.
> Individual-level genotype calls and the pairwise kinship matrix produced by the
> sample-identity screen are not redistributed, because a genotype matrix is identifying
> in principle and the source datasets' terms restrict redistribution of individual-level
> data; the summary statistics reported in the Methods, and the code that regenerates the
> full output from authorised access to the primary data, are both in the deposit.

> **Code availability.** All analysis code is available at
> https://github.com/pchureer/cardiac-splicing-dcm-hcm and archived at Zenodo
> under DOI 10.5281/zenodo.23681815. The repository's `CONVENTIONS.md` states the three
> conventions a reader needs in order to reproduce the published counts — in particular
> that the exon-level significance rule is applied **after** collapsing rMATS rows to
> event coordinates, which changes the answer.

## 3. ⚠ Reserve the DOI, do not wait for it

The manuscript cannot be submitted with a placeholder where the DOI goes, and the DOI
is normally issued at publication — which is after submission. Zenodo resolves this:

1. Create the Zenodo upload (**New upload**), fill the metadata, and do not publish.
2. Under *Basic information → Digital Object Identifier*, choose **Reserve DOI**. Zenodo
   issues the DOI immediately and it resolves once you publish.
3. Put that reserved DOI in the manuscript, in both statements above, and in
   `CITATION.cff` in the deposit.
4. Publish the Zenodo record when the manuscript is submitted, not before — a published
   record cannot have its files changed, only superseded by a new version.

Set the GitHub repository's Zenodo integration **before** you tag a release if you want
Zenodo to archive the repository automatically; the integration only picks up releases
created after it is switched on.
